1. SYSTEM ARCHITECTURE & HYBRID OPERATIONAL OBJECTIVES
================================================================================

1.1 High-Level Purpose
The QRYPTONEX Hybrid Suite implements a dual-layer cryptographic defense
designed to provide Post-Quantum Forward Secrecy and Post-Quantum Authenticity
while preserving the battle-tested classical security guarantees of Curve25519.

Even if an adversary possesses a cryptanalytically relevant quantum computer
(CRQC) capable of breaking discrete logarithms (Shor's algorithm), the post-
quantum primitives (ML-KEM-768 and ML-DSA-65) ensure confidentiality and
authenticity remain intact. Conversely, if an unforeseen mathematical flaw is
discovered in lattice-based cryptography, the classical primitives (X25519 and
Ed25519) guarantee full 128-bit classical security.

1.2 Fail-Closed Core Principle
The hybrid suite adheres strictly to fail-closed semantics:
  - Both key exchanges (X25519 and ML-KEM-768) must succeed and contribute to
    the final shared secret. No single-mechanism fallback is ever permitted.
  - Both signatures (Ed25519 and ML-DSA-65) must verify cleanly against the
    peer identity keys. If either signature verification fails, the connection
    aborts instantly with zero key material derived.

5. DUAL KEY ENCAPSULATION & SHARED SECRET COMBINER
================================================================================

Let SS_c = X25519(sk_client_eph, pk_server_eph)   [32 bytes]
Let SS_pq = ML-KEM-768-Decap(ct, sk_client_kem)   [32 bytes]

The raw combined secret is concatenated:
  Raw_SS = SS_c (32 bytes) || SS_pq (32 bytes)    [64 bytes]

To protect against pre-computation and multi-target attacks, domain-separated
HKDF-SHA-384 is used to extract the Master Shared Secret:

  Master_Secret = HKDF-Extract(
      salt = client_nonce (16 bytes) || server_nonce (16 bytes),
      IKM  = Raw_SS (64 bytes)
  )  --> 48 bytes (SHA-384 output length)

================================================================================
6. DUAL DIGITAL SIGNATURES & NON-SEPARABLE COMPOSITE AUTHENTICATION
================================================================================

To guarantee non-repudiation and prevent stripped-primitive attacks:
1. The transcript digest H_transcript is computed over the cumulative handshake
   messages using SHA-384.
2. The sender computes BOTH:
   - Sig_c  = Ed25519_Sign(H_transcript, sk_ed25519)   [64 bytes]
   - Sig_pq = ML-DSA-65_Sign(H_transcript, sk_mldsa65) [3309 bytes]
3. The composite signature is:
   Sig_hybrid = Sig_c (64 bytes) || Sig_pq (3309 bytes) [3373 bytes]
4. The receiver verifies:
   - Ed25519_Verify(H_transcript, Sig_c, pk_ed25519) == VALID
   - ML-DSA-65_Verify(H_transcript, Sig_pq, pk_mldsa65) == VALID
   If either verification returns non-zero, the connection is instantly rejected.

7. DIRECTIONAL KEY DERIVATION (HKDF-SHA-384)
================================================================================

Independent directional keys are derived from Master_Secret:

  Client_Write_Key (32B) = HKDF-Expand(
      PRK  = Master_Secret,
      info = "QRYPTONEX-HYBRID-c2s" || session_id (8 bytes),
      L    = 32 bytes
  )

  Server_Write_Key (32B) = HKDF-Expand(
      PRK  = Master_Secret,
      info = "QRYPTONEX-HYBRID-s2c" || session_id (8 bytes),
      L    = 32 bytes
  )

8. CHACHA20-POLY1305 & WIRE HEADER AAD BINDING
================================================================================

All post-handshake packets (PKT_DATA) are encrypted with ChaCha20-Poly1305.
The 15-byte packet wire header is bound as Additional Authenticated Data (AAD):

  AAD = [ seq (4B, big-endian) || type (1B) || len (2B, big-endian) || session_id (8B, big-endian) ]

Wire Payload:
  [ Nonce (12B) || Poly1305 Tag (16B) || Ciphertext (N bytes) ]

Total Wire Size = 15 (Header) + 12 (Nonce) + 16 (Tag) + Plaintext_Length bytes.

Nonce Construction:
  Nonce = [ Little-Endian 64-bit Counter (8B) || 0x00000000 (4B) ]
  Guarantees strict monotonicity without nonce-reuse risks.

================================================================================
9. RFC 6479 SLIDING REPLAY WINDOW
================================================================================

Each session maintains an independent 64-packet bitmap replay window:
  - Any packet sequence number seq < max_seq - 64 is dropped immediately.
  - Any packet sequence number whose bit in the window mask is set is dropped
    as a duplicate.
  - State is committed to the window only AFTER successful Poly1305 tag
    verification (pre-auth check prevents state corruption; post-auth update
    prevents replay attacks).
