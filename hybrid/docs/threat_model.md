# QRYPTONEX Hybrid Threat Model & Security Evaluation

## 1. Scope & Objective

This threat model evaluates the security posture of the **QRYPTONEX Hybrid Cryptographic Suite** (`QRYPTONEX-HYBRID-X25519-MLKEM768-ED25519-MLDSA65`). The system is evaluated against an active network adversary capable of intercepting, replaying, injecting, reordering, and corrupting network traffic, as well as storing encrypted sessions for future decryption using cryptanalytically relevant quantum computers (CRQCs).

---

## 2. Adversary Model & Assumptions

### 2.1 Adversary Capabilities
- **Full Dolev-Yao Network Adversary**: The attacker controls the communication link between client and server, able to drop, inject, delay, duplicate, and modify any wire packet.
- **Harvest-Now-Decrypt-Later (HNDL)**: The adversary captures and archives all transmitted encrypted sessions today to decrypt them once a CRQC becomes available.
- **Quantum Signature Forgery**: The adversary possesses a quantum computer capable of running Shor's algorithm to solve discrete logarithms and elliptic curve discrete logarithms in polynomial time.
- **Classical Computing Power**: Standard classical cryptanalytic computational bounds ($< 2^{128}$ operations).

### 2.2 Security Guarantees Intended
1. **Confidentiality against Classical Adversaries**: Protected by X25519, ML-KEM-768, and ChaCha20-Poly1305. Breaking confidentiality requires breaking *both* X25519 and ML-KEM-768.
2. **Confidentiality against Quantum Adversaries**: Protected by ML-KEM-768 (FIPS 203) and 256-bit ChaCha20 keys. Even if Shor's algorithm solves X25519, ML-KEM-768 prevents derivation of the session key.
3. **Mutual Authentication Integrity**: Both Ed25519 and ML-DSA-65 signatures are mandatory. An adversary cannot authenticate as a peer unless they compromise *both* private identity keys.
4. **Downgrade Immunity**: Protocol versions and cipher suite identifiers are cryptographically bound into the canonical transcript digest.
5. **Replay Immunity**: Monotonically increasing sequence counters combined with an RFC 6479 sliding replay window prevent message replay and duplicate acceptance.
6. **Forward Secrecy**: Ephemeral key exchange secrets ($SK_{\text{x25519}}$, $SK_{\text{mlkem}}$) are discarded and zeroized immediately after key derivation.

## 3. Threat Analysis & Mitigations

### 3.1 Quantum Computing Threats & HNDL

| Attack Vector | Impact on Classical Primitive | Impact on Post-Quantum Primitive | Combined Hybrid Posture |
|---|---|---|---|
| **Shor's Algorithm on Key Exchange** | X25519 ECDH broken in polynomial time ($O(n^3)$). | ML-KEM-768 (Module-LWE) unaffected by Shor's algorithm. | **Protected.** Derived session key relies on length-prefixed IKM. The attacker lacks $ss_{\text{mlkem}}$, preventing derivation of PRK. |
| **Shor's Algorithm on Authentication** | Ed25519 broken in polynomial time. | ML-DSA-65 (Module-LWE/SIS) unaffected. | **Protected during migration.** Both signatures must pass. Quantum adversary cannot forge ML-DSA-65 signature. |
| **Grover's Algorithm on Symmetric Ciphers** | AES-128 effective security reduced to 64 bits. | ChaCha20 with 256-bit key has 128-bit quantum security. | **Protected.** ChaCha20-Poly1305 uses full 256-bit keys, exceeding NIST Level 3 post-quantum security requirements. |
| **Grover's Algorithm on Hash Functions** | SHA-256 collision resistance reduced to 85 bits. | SHA-384 provides 192-bit quantum collision resistance. | **Protected.** Handshake transcript and HKDF use SHA-384. |

### 3.2 Downgrade Attacks

- **Threat**: An active attacker intercepts `CLIENT_HELLO` and rewrites the version field or substitutes the cipher suite identifier with a classical-only suite (e.g. X25519-AES128-CCM) to force the parties into a vulnerable mode.
- **Mitigation**:
  1. The server strictly rejects any offered version other than `0x0100` with `HYBRID_ERR_VERSION_UNSUPPORTED`.
  2. The server strictly rejects any suite other than `QRYPTONEX-HYBRID-X25519-MLKEM768-ED25519-MLDSA65` with `HYBRID_ERR_DOWNGRADE_DETECTED`.
  3. The version and suite ID are explicitly hashed into the canonical Server Transcript. Any tampering causes the Server Transcript Digest to diverge, resulting in dual signature verification failure.

### 3.3 Replay Attacks

- **Threat**: An attacker captures a valid handshake message or application packet and replays it at a later time.
- **Mitigation**:
  1. **Handshake Nonces**: Client and server exchange fresh 32-byte nonces generated by the OS CSPRNG. Handshake transcripts incorporate both nonces, ensuring transcripts and session keys are unique across every connection.
  2. **Sliding Replay Window**: Application packets implement RFC 6479 with a 64-packet window. Duplicate sequence numbers and packets older than the 64-packet window are rejected.
  3. **Two-Phase Replay Verification**: The replay window check occurs prior to AEAD tag decryption without advancing state; the window state commits only after cryptographic authentication succeeds, preventing denial-of-service state corruption.

### 3.4 Identity Substitution & Man-In-The-Middle (MITM)

- **Threat**: An attacker generates their own keypair and presents it to the peer, claiming to be the authentic server or client.
- **Mitigation**:
  1. **Dual Signature Requirement**: Handshake messages must carry valid signatures from *both* Ed25519 and ML-DSA-65.
  2. **Trust Store Pinning**: Clients pin the expected server public key. If the incoming public key does not match the pinned reference, the connection is aborted with `HYBRID_ERR_UNTRUSTED_PEER`.
  3. **Authorized Client Enrollment**: Servers verify client identity public keys against an authorized peer database.

### 3.5 Key Compromise & Forward Secrecy

- **Ephemeral Key Zeroization**: Ephemeral private keys and intermediate shared secrets are erased using `hybrid_cleanse()` (`explicit_bzero`) immediately after the HKDF-Extract step.
- **Forward Secrecy**: Compromise of long-term identity keys allows impersonation in future connections, but does not allow passive decryption of past recorded sessions because session keys are derived from ephemeral X25519 and ML-KEM secrets.

### 3.6 Nonce Reuse & Nonce Exhaustion

- **Threat**: Reusing an AEAD nonce with ChaCha20-Poly1305 catastrophically destroys authenticity and leaks the Poly1305 one-time key.
- **Mitigation**: Nonces are generated monotonically from a 64-bit counter: $\text{Nonce} = \text{le64}(\text{tx\_nonce\_ctr}++) \parallel 0x00000000$. Encryption is halted before counter exhaustion ($2^{64}-256$) with `HYBRID_ERR_NONCE_EXHAUSTED`.

## 4. Limitations & Outstanding Review Requirements

> [!WARNING]
> While this hybrid implementation adheres to FIPS 203, FIPS 204, RFC 7748, RFC 8032, and RFC 8439 standards, it is an independent research implementation. The following items require formal independent cryptanalytic and engineering review before production deployment:

1. **Independent Cryptographic Audit**: The composite dual signature scheme and transcript binding format should undergo formal verification (e.g., using ProVerif or CryptoVerif) to verify freedom from unknown cross-protocol attacks.
2. **Side-Channel Analysis**: While OpenSSL and liboqs strive for constant-time implementations, physical side-channel leakages (power analysis, EM emanations, and cache timing) on embedded devices require dedicated physical measurement.
3. **Formal Verification of State Machine**: State transition logic in `hybrid_handshake.c` should be verified for deadlock-free and fail-closed termination under all network fault conditions.
4. **Certificate & PKI Integration**: Identity keys are currently pinned via raw public keys. Integration with an X.509 or CBOR-based post-quantum PKI is recommended for large-scale multi-party deployments.
